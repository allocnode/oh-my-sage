# MCP 效率优化方案

状态：第一阶段已实现（本文第 3 节），其余为后续计划。

## 1. 问题在哪

一次中等规模的修改（3 条规则、约 30 个节点、同步更新备注）耗时远超预期。逐个计时后发现，瓶颈不在 MCP 服务本身：

| 调用 | 耗时 | 返回体积 |
|---|---|---|
| `mijia_status` | 约 10 ms | 18 B |
| `mijia_get_graph` 摘要（97 个节点的规则） | 约 100 ms | 19.5 KB |
| `mijia_get_graph` 指定 3 个节点 | 约 96 ms | 1.2 KB |
| `mijia_get_graph` 完整 | 约 102 ms | 33.3 KB |
| `mijia_validate_graph` | 约 95 ms | 72 B |
| `mijia_validate_graph_capabilities` | 约 164 ms | 119 B |
| `mijia_find_device_usage`（扫描 40 条规则） | 约 460 ms | 2.9 KB |
| `getLog`（经 `mijia_call_api`） | 约 264 ms | 原始约 1 MB，被截断 |

整次修改里所有 MCP 调用加起来不到一分钟。时间耗在模型一侧：

1. **来回轮次多**：每读一次、想一次、写一次就是一轮，每轮生成要几十秒，与工具快慢无关。
2. **读进来的太多**：大规则摘要约 19 KB，同一条规则被反复读，大部分内容与要改的地方无关。
3. **写出去的太啰嗦**：每个节点都要写完整 JSON（`cfg.name`、`cfg.version`、`cfg.urn`、`inputs` 端口声明、`outputs` 数组、`dtype`、作用域字符串）。7 个节点就要手写约 3 KB，而生成输出是模型最慢的环节。
4. **零碎步骤多**：两次单独校验、回读、单独建变量、先读一遍防重名、手工按下标拼备注富文本，每一步都是额外一轮。

所以根本办法不是让 MCP 更快，而是「一次修改只需一次小调用、只拿回一份小结果」。

## 2. 设计原则

- **紧凑文本作为读写的主格式**：一行一个节点，固定内容由服务端补全。
- **无损是硬要求**：任何节点无法用简写完整表达时，退回「简写 + 差异」或原始 JSON 行，绝不丢字段。所有在线规则必须能通过往返测试。
- **一次调用完成一次修改**：建变量、改节点、改备注、两项校验、写入、回读合并为一个事务，失败时回滚本次新建的变量。
- **不重复传已知内容**：只读需要的节点；内容没变时只回 hash。
- **能在服务端做的筛选就在服务端做**：跨规则查询、日志过滤都只返回命中部分。

## 3. 第一阶段（已实现）

| 内容 | 位置 |
|---|---|
| 紧凑文本格式（编码、解码、无损兜底、设备名称解析、`@tts`/`@pulse` 宏、`var` 声明） | `src/core/tools/ruleText.ts`，说明见 `docs/rule-text-format.md` |
| 备注 Markdown 互转与段落操作（追加、替换、变更记录、自动调整高度） | `src/core/tools/ruleNote.ts` |
| `mijia_get_graph` 新增 `format:"text"`、`focus`/`depth`、`ifNoneMatch` | `src/mcp/tools/graph.ts` |
| `mijia_patch_graph` 新增 `add`（重名拒绝）、`replace`（不存在拒绝）、`note`、`variables`、`dryRun`，返回改动明细文本 | `src/core/tools/graphText.ts` |
| `mijia_create_graph` 支持 `text` | `src/mcp/tools/graph.ts` |
| 新工具 `mijia_put_graph_text`：用完整文本替换规则 | 同上 |
| 新工具 `mijia_query_rules`：按变量、设备属性、节点类型跨规则查询 | 同上 |
| 新工具 `mijia_get_log`：按规则、节点、时间过滤日志，可只看执行次数 | 同上 |
| 规则文件同步脚本 `pull`/`push`/`status` | `scripts/rules.mjs` |
| 在线往返检查脚本 | `scripts/check-rule-text.mts` |

实测（40 条规则、795 个节点）：

- 全部无损往返，没有任何节点需要退回原始 JSON。
- 紧凑文本约为 JSON 摘要的 49%；写入时只写有意义的部分，通常约为同等 JSON 的五分之一。
- 修改一条规则从「读摘要 → 按需取节点 → 查重名 → 建变量 → 写入 → 校验两次 → 回读」变为「读文本 → 一次 `mijia_patch_graph`」。

## 4. 后续计划

1. **宏扩充**：`latch`（带重启复位的上升沿锁存）、`idleTimer`（有动静就重新计时）、`elapsed`（`now()` 时间差）。先确认这些结构在多条规则里确实重复出现再做。
2. **执行轨迹与状态快照**：`mijia_trace` 把某条规则最近几次执行串成一行（如 `开门 → 已空 183 秒 → 通过 → 置 1`）；`mijia_snapshot` 一次读出规则用到的全部变量和设备属性当前值。
3. **Skill 瘦身**：有了文本格式，Skill 中的整段 JSON 节点模板可以删掉，只保留流程与硬性规则；经验记录按主题拆分。
4. **离线试跑（可选）**：用记录下来的真实事件序列模拟规则触发。需要在本地复现网关执行语义，代价较高，只针对已实机验证过语义的节点类型。

## 5. 不做的事

- 为读取加缓存降低延迟：读取本来只要约 100 ms。
- 增加并发：调用已经很快，大量并发反而会在部分客户端刷出警告。
- 在 MCP 里接入传感器历史：网关只记录规则执行，不保存设备上报历史，这类分析应在外部完成。

## 6. 衡量方式

重复一次同等规模的修改，对比工具调用次数、返回给模型的字节数、模型写出的字节数。目标：每条规则一读一写，每条规则返回不超过 5 KB。
