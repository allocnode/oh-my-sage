# 通用经验与反例

## 变量引用不是变量创建

在规则节点中填写 `id` 和 `scope` 不会创建变量。变量必须先登记；否则网关可能接受规则，但极客版页面会显示变量丢失。创建或更新规则前应验证变量存在和类型兼容。

## 网关接受不等于规则可运行

证据至少分为三层：

1. 网关接受并能回读。
2. 极客版页面能重新打开且不丢字段。
3. 运行时产生预期结果。

连接语义错误可能通过网关保存，因此结构校验和运行验证不能互相替代。

## 条件需要触发与状态两个来源

`condition.trigger` 决定何时判断，`condition.condition` 提供当时状态。缺少任一来源都不能形成有效的“当-如果-就”。实测中 condition 未连接时不会执行 `met`。

当前网关实测：事件先到、状态约 500 ms 后才变真时不会回补前一次事件；同次求值中明确 false 会走 `unmet`。需要“状态后来成立也执行”时，状态变化本身必须成为触发。

## 限制次数不等于停止循环

`onlyNTimes` 或动作侧计数只能阻止后续动作，不会自动停止 loop 定时器。当前网关已验证 `counter(n=3) → loop.stop` 可将循环精确停止在第 3 轮。

## 模式空档仍推进游标

当前网关已验证三档 `modeSwitch` 中第三档输出为空时，前两档各执行一次后第三次仍进入空档并停止该链。空输出不是自动跳过；重启后游标位置仍需单独验证。

## 外部通知与同规则回声不同

`deviceInputSetVar` 已验证能接收实体设备外部变化。由同一规则写入设备后，网关可能抑制回声通知以避免循环；不要把这类行为直接判定为节点失效，也不要依赖自触发回环。

## 数值量化不是显示格式化

`round(x*10^N)/10^N` 得到数值结果，不保证文本显示固定 N 位尾零。播报和显示格式需要单独验证。

## 双向同步不能只看差值

差值归零只证明稳态相等。可靠双向同步还要处理来源、去抖、容差、量化、同时操作、离线恢复和最大执行次数。

## 视频案例保留冲突

口述、字幕、公式和画面冲突时，不选择一个方便的版本冒充事实。将案例标为 `conflicted`，等待 UI 样本、规则 diff 或运行证据。

视频中的运行演示也不能替代可复核的规则、日志和设备结果三者对应。单个画面支持某个现象时，只升级对应边界，不升级整个拓扑。

## 私有证据不进入公开知识

家庭设备 ID、网关地址、门锁参数、人员信息、事件时间和本机路径只保留在私有案例库。公开模式使用合成名称和脱敏结构。

## 读回设备属性可能命中陈旧缓存

`deviceGet` 和 `deviceGetSetVar` 返回的是网关侧可用的属性值，靠设备上报刷新。实测中该值在写入后 **超过 10 秒仍可能是旧值**。

由此产生一个典型误判：验证「变量动态设置设备属性」是否生效时，在同一条链里写完立刻读回，读到旧值，于是错误结论「该能力不可用」。实际写入是成功的。

验证设备写入必须满足：

- 拆成两条独立规则，一条只写、一条只读，中间间隔 20 秒以上；
- 使用独特测试值（不要用设备当前值或常见默认值），否则无法区分「写成功」与「本来就是这个值」；
- 测完把属性还原并删除临时规则。

安全相关判断同理，不能只依赖一次查询结果。

## 变量之间的链式读写没有延迟

与设备属性相反：同一条链里 `varSetNumber` 写入的变量，紧接着的下游节点立即可读到新值。对照实验 `A=12345 → B=$A+1` 读回 `B=12346`。

排查数值异常时先区分这两者，不要把「设备属性缓存」的结论套到「变量传递」上。

## 时长换算不要卡在整分边界

`起点 = now()` 与「持续 N 秒后触发」由两个不同时刻写入，节点执行有先后差。60 秒定时触发时实际时长常为 59700 毫秒左右，`floor(x/60000)` 得到 0 而不是 1。

修法是同时加余量和下限：

```text
分钟数 = max(1, floor((时长毫秒 + 2000) / 60000))
```

余量吸收系统性负偏移（影响每一次计算，不只第一次），下限兜住按设计不可能出现的 0。

更通用的规则：凡是「时间差 → 取整 → 整数单位」，都要检查典型输入是否恰好落在临界点上。定时器驱动的时长天生落在临界点。

## 条件文案用分支写同一个字符串变量

`varSetString` 的 `elements` 是固定拼接，没有条件表达式。需要按条件切换用词时：

```text
数值计算 → varGet(标志位) ─┬─ output  → varSetString(词 = "甲")
                          └─ output2 → varSetString(词 = "乙")
                                          ↓ 两条汇合
                          varSetString(整句 = 前缀 + 数字 + 词 + 后缀)
```

两个分支写**同一个字符串变量**，再汇合到同一个拼接节点。`varGet` 两条输出互斥，只会执行一条。

配套已验证结论：`elements` 可以连续放多个 `var` 元素；多个不同节点写同一个变量不会互相干扰。

需要「半单位」粒度（如一分半）时不要用小数（`1.5` 会被读成「一点五」）。改成以半单位计数再拆整数与余数：

```text
半单位数 = floor(时长 / 半单位长度)
整数部分 = floor(半单位数 / 2)
是否带半 = 半单位数 % 2
```

`varSetNumber` 支持 `%`，这是拆奇偶的关键。

## preload 决定规则启用瞬间是否评估一次

实测结论：

- `preload: true` — 规则启用时立即按属性当前值评估，匹配则触发一次，全程无需设备状态变化；
- `preload: false` — 启用时不触发，只在属性发生变化时触发。

对照实验：同一属性上并列「等于 true」和「等于 false」两个触发器，各接一个计数变量。`preload: true` 时与当前值匹配的那个计数为 1、另一个为 0；改成 `false` 后两者均为 0。

因此 `preload` 不是「必须为 false」。选择依据是**规则启用时是否应当立即对齐当前状态**：

- 需要启用即生效的状态同步、清理类规则可用 `true`；
- 多个触发器会在启用瞬间同时评估并可能相互冲突时必须用 `false`，例如双向同步的四分支结构。

## 设备未暴露或能力名不副实时可借语音助手执行

厂商自填的 `desc` 不是语义保证。曾遇到某网关类设备只暴露一个名为「开关状态」的可写布尔属性，实际是内部检索操作，写入不会关闭下挂设备。网关类、桥接类设备的单个布尔属性尤其不能望文生义。

目标设备未接入网关、或暴露的能力不可用时，可以把智能音箱当作执行层：调用其「执行文本指令」动作（与「播报文本」是不同的动作 ID），并把「静默执行」参数置真，使助手直接执行而不复述。

代价是能否生效取决于 App 侧的设备命名与分组，网关侧无法校验，必须实机测一次；但指令文本是纯字符串，调整成本极低。

## 复制已有规则建新规则时要补 var 声明

`mijia_get_graph format="text"` 读出的已有规则只有对 `$R.名` 的引用，不带 `var` 声明行，因为那些变量早已存在。把这段文本照搬给 `mijia_create_graph`，新规则的作用域和变量都还不存在，写入前的能力校验会报 `Scope R<新规则ID> does not exist` 并拒绝创建（不会写入网关）。

做法：复制前列出文本里所有 `$R.名`，每个补一行 `var $R.名 类型 初始值 "显示名"`，再提交。给已有规则新增变量时同理，用 `mijia_patch_graph` 的 `variables` 或 `add` 里的 `var` 声明。
